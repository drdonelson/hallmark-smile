Overview

What This Is

A patient-facing AI smile simulator embedded on dental practice websites. Patient takes a selfie in the dental chair; the simulator generates a photorealistic "after" showing a full cosmetic makeover — Dr. Apa–style golden proportion symmetry, individually defined teeth with visible embrasures, BL1 whitening. Goal: patient emotionally commits to treatment before leaving the chair.

Business model

  • SaaS via Lucid ROI platform
  • White-labeled embed via ?theme= param
  • Lead capture → dentist dashboard

Competing product

  • bitebot.io — same category
  • Further ahead on output quality
  • Closing the gap is the primary technical goal
Note: Dr. David Donelson (dentist/founder) pushes directly to this repo. Always pull before you push. He also edits worker.js directly for business logic additions.
Architecture

Current Pipeline Architecture

Patient selfie (mobile camera)
    ↓
MediaPipe 468-point face mesh  (runs browser-side, landmarks never leave device)
    → inner-lip polygon → tooth bounding box + mask PNG
    ↓
ideogramCropMakeover()  ← PRIMARY PATH
    1. Perioral ellipse edit zone  (rx 0.85·tbW, ry 2.5·tbH)
    2. Crop from FULL-RES photo, scale to 1024px longest side
    3. Tooth erase: fill tooth pixels rgb(20,12,12) — forces generation from scratch
    4. Bib desaturation below ellipse (strips teal dental bib color)
    5. Ideogram v2 inpaint via Replicate (BLACK=edit, WHITE=preserve)
    6. Best-of-2 parallel draws — scored by embrasure + coverage − glare
    7. Pixel-precise blend mask (MP brightness→alpha) → composite to original face
    ↓
Fallback chain (each fires only if primary throws):
    [2] gpt-image-2 crop-zoom (OpenAI)
    [4] FLUX Pro Fill full image (fal.ai)
    [6] Client-side HSL whitening  ← always works, lowest quality
    ↓
After image displayed → VIDEO PREGEN starts immediately
    → Seedance v1 lite (fal.ai): 8s/720p, patient mouths "this is amazing" + laughs
    → "Watch Video" button attaches to already-running job → perceived wait ~0
    ↓
Email: before + after → patient + dentist (Resend API, hosted R2 URLs)
Fallbacks 1, 3, 5 are dead — Modal A10G and RunPod are defunded as of June 2026. LoRA weights survive on HuggingFace.
Competitive Analysis

What Bitebot Does Differently

We've compared bitebot's before/after pairs extensively. Their output shows consistent signals of full lower-face regeneration, not tooth inpainting:

Signal in bitebot outputWhat it implies
Hair and upper face are pixel-identical to before NOT doing full-face AI — upper face is preserved
Smile is noticeably wider than original anatomy allows Regenerating more than just teeth — perioral zone is included
Lip shape and support change between before/after Lower face (lips, gum, perioral) is regenerated as a unit
No visible composite seam anywhere Edit zone boundary falls on cheek skin, outside the face expression area
Every case gets full arch canine-to-canine Not constrained by original tooth detection — fills full ellipse
Their likely approach: Inpaint a large perioral ellipse (teeth + gums + lips) so the blend boundary falls on cheek skin where any seam is invisible, then regenerate everything inside as a coherent unit. We now do this too — the remaining gap is ellipse calibration and potentially a fine-tuned model.
Iteration History

Full Iteration History

Every approach tried, from first commit to now — what we learned from each.

01

Brightness-threshold masking

Dead

Built buildToothMask() using HSV/brightness to find white pixels. Finds ~628 pixels. Misses yellowish, stained, decayed teeth entirely. Never use — buildMediaPipeMask supersedes it completely (finds 6,000+ pixels geometrically regardless of tooth color).

02

ControlNet + LoRA full-face inpaint (Modal A10G)

Dead

SDXL + dental LoRA (456MB, trained on ~600 Instagram before/after pairs). Ran at 1024px full-face — tooth region only ~200px wide. Cannot render individual tooth anatomy at 200px. Additional failure: LoRA img2img had no workable strength range (≥0.70 → white slab, <0.70 → too subtle). Modal/RunPod defunded June 2026. LoRA weights on HuggingFace (drdonelson/dental-lora).

03

FLUX Pro Fill crop-zoom

Fallback

Crop mouth region, zoom to 1024px, FLUX inpaint. Mask convention: WHITE=edit (opposite of Ideogram). Decent results but Ideogram v2 consistently outperforms on tooth anatomy detail. Now Fallback 4.

04

Ideogram v2 crop-zoom — primary

Live (Primary)

Crop to tooth region at 2.0×/1.5× padding, scale to 1024px. Teeth fill most of the Ideogram input — 5× more compute on the relevant zone. Core sub-discoveries:

  • Tooth erase — fill MP-detected teeth with rgb(20,12,12) before sending. Without this, Ideogram sees existing light teeth and barely changes them → white slab. Dark fill = "missing teeth" signal = full generation from scratch.
  • Mask convention — Ideogram v2 uses BLACK=edit, WHITE=preserve. FLUX/SDXL are the opposite. Getting this backwards silently edits the face.
  • Bib desaturation — patients wear teal bibs. Ideogram samples context → blue teeth. Fix: desaturate all pixels below the tooth zone.
  • Pixel-precise blend mask — bbox rectangle blend → visible rectangular seam. MediaPipe mask brightness→alpha → blend follows exact tooth geometry.
  • Commissure fade — INNER_LIP polygon traces to mouth corners. Ideogram drifts there → fade blend to 0 over outer 5–10% of tooth width.
  • destination-in alpha trap — clips by source ALPHA not color. Black (alpha 255) = opaque. Blend mask canvas must default transparent.
05

Lighting harmonization (harmonizeTeeth())

Live

After compositing Ideogram teeth, they looked "pasted on" — too cool, too bright. Built LAB color space illuminant transfer: sample scene color temperature from perioral skin only (warm pixels: LAB a > 4) — not whole crop (white walls contaminate and cyan-shift the teeth). Transfer ~half the chroma shift, match brightness to skin highlight level, apply per-column light falloff.

06

Collapsed/edentulous detection

Live

Full-arch tooth loss → nearly closed mouth → inner-lip bbox aspect <0.18 (normal smiles: 0.22–0.26). When collapsed: tight 0.5×/1.0× padding, vertical mask expansion, perioralSmile prompt, harmonization disabled.

07

Perioral ellipse for edentulous cases

Live

Tooth-confined inpainting can't restore lip support — bounded by original lip line. Fix: draw perioral ellipse (rx=0.72·tbW, ry=2.2·tbH) covering full mouth opening including lips. Ideogram regenerates entire smile zone. 5/5 validated. Shipped June 2026.

08

Best-of-2 QC

Live

Ideogram has large run-to-run variance. Run 2 parallel draws, score both with scoreToothGeneration() (embrasure local-minima + tonal stddev − cold glare penalty + coverage fill ratio), keep higher score. ~$0.16/run.

09

Perioral ellipse for ALL cases (attempt 1)

Reverted

Applied perioral ellipse to all patients with rx=0.85·tbW, ry=1.6·tbH. On patients with intact existing teeth, Ideogram generated a grotesquely wide, anatomically impossible "clown smile." Reverted within hours while live on Seven Bridges Dental. Root cause: ry=1.6 cuts through the smile arc — vertical opening too small relative to horizontal, creating an unnatural mouth shape that Ideogram can't resolve plausibly.

10

Hires geometry — tight crop from full-res photo

Live

Production crop (2.0×/1.5× padding) spans nearly the full image → teeth hit Ideogram at ~205px, no real zoom benefit. Switch to: crop from the full-resolution original (not the downscaled working image), tight 0.5×/1.0× padding, ~3:1 AR matching Ideogram's native output. Teeth now ~500px wide at Ideogram — dramatically sharper anatomy.

11

Perioral ellipse for ALL cases (attempt 2) — current

Live

Re-applied perioral approach to all cases with better calibration: rx=0.85·tbW, ry=2.5·tbH (larger vertical than the failed attempt's 1.6), openSmile/perioralSmile prompt. Larger ry prevents the ellipse from cutting through the smile arc. Validated across 7 case types. No clown-face artifacts.

12

Severe damage routing

Live

Measure average brightness of original tooth pixels. If avgBright <90 → route to fullArch Ideogram variant. The normalSmile prompt negated "wider smile, different smile width" — exactly wrong for heavily decayed teeth. fullArch prompt explicitly requests "premolars visible toward the corners" and "broad confident smile arc."

Critical Worker Constraints

Cloudflare Worker has a 30-second subrequest limit. Ideogram takes 20–90s. The Worker CANNOT wait for it. Pattern: Worker starts the Replicate prediction → returns prediction ID → browser polls /api/replicate/status?id=X every 4s. Same async pattern applies to all long-running jobs.

Ideogram v2 Specifics

  • Mask convention: BLACK = edit zone, WHITE = preserve (opposite of FLUX/SDXL — this has burned us before)
  • Output is always ~3:1 aspect ratio regardless of input. A 5:1 input → 3:1 output with quality loss. Keep crop AR near 3:1.
  • Cost: ~$0.08/image, ~$0.16/run with best-of-2

Roadmap

Two Paths Forward

Path A — Closing the Gap Without Training Data

Achievable with Ideogram inpainting as-is. Estimated developer time per item:

1. Aperture parameter sweep — 2–4 hours

The perioral ellipse rx/ry (0.85 width, 2.5 height) is a single fixed value for all cases. Larger ry → more lip area regenerated → closer to bitebot. But too large → identity drift. Need 10+ patient test photos to find the stable ceiling. Add rx/ry tunable params to harness UI and run a grid search.

2. Artifact detection + auto-retry — 3–5 hours

scoreToothGeneration() already runs on both best-of-2 draws. Add a minimum score threshold — if BOTH draws score below it, run a 3rd draw. Catches ~15% of runs that produce slabs or partial arches. Adds $0.08 and ~30s to those cases only.

3. Gum-band anchor for gum-showing smiles — 4–8 hours

Full tooth erase leaves Ideogram no gingival anchor → dark void above generated teeth on gum-showing patients. Research in harness (gum=0.25): preserve top 25% of each tooth column globally if ≥40% of columns have healthy pink gum. Per-pixel or per-column decisions both fail (decay pixels and striping artifacts). Global per-photo decision is clean. Validated at hires crop; needs production crop validation.

4. FLUX Kontext as alternative primary — 1–2 days exploratory

FLUX Dev Kontext (mid-2026) takes a reference image and follows transformation instructions — no mask needed. "Replace the teeth with BL1 veneers, keep everything else." Could sidestep Ideogram's inpainting constraints entirely. Quality on dental cases is unknown. Worth a harness proof-of-concept. Cost: ~$0.06/image.

Path B — Training Data (Closes the Bitebot Gap)

This is the path to truly matching or beating bitebot. Their quality edge almost certainly comes from a fine-tuned model.

Training data status: ~600 before/after pairs exist from a dentist friend's Instagram, but they are NOT commercially licensed. Commercial training on friends' patients needs a written partner agreement (privacy + copyright). Dr. D's OWN practice archive (e.g., the _DSC1529/_DSC3401 pair) is clean and usable immediately.

FLUX Kontext LoRA fine-tuning

FLUX Dev Kontext LoRA needs only 50–150 before/after pairs (far less than Stable Diffusion). Dr. D's own archive may already have enough for an initial model.

Pair requirements: matched lighting, same face position, full-face (not crops), minimum 3 case types (mild whitening / veneer makeover / full-arch restoration).

What a fine-tuned model changes:

  • No mask needed — model understands "cosmetic dental makeover" as a transformation
  • Full perioral coherence — lips, gum, teeth regenerated as a unit because the model saw real results
  • No bib desaturation hack — model learns to ignore bibs from training data
  • Eliminates run-to-run variance — trained signal is consistent, not zero-shot prompting
  • Cost: ~$0.06/image inference, ~$30–80 to train on Replicate

Training workflow

  1. Curate 50–100 pairs from Dr. D's own archive (or partner practice with written consent)
  2. Fine-tune FLUX Dev Kontext LoRA on Replicate or fal.ai (both have hosted training)
  3. Deploy the fine-tuned version on Replicate
  4. Replace ideogramCropMakeover() with a full-face FLUX Kontext call
  5. Keep current Ideogram pipeline as fallback

Path A timeline

  • Week 1: Aperture sweep + artifact retry
  • Week 2: Gum-band anchor + FLUX Kontext POC
  • Gets closer, doesn't fully close gap

Path B timeline

  • Week 1–2: Curate + license 50+ pairs
  • Week 2–3: Fine-tune + evaluate
  • Week 3–4: A/B test + ship
  • Should close the bitebot gap entirely
Know Before You Start

Hard Constraints

ConstraintWhy It Matters
CF Worker 30s limit All AI calls must be async. Never await a long job inside the Worker. Start → return ID → browser polls.
Ideogram mask is BLACK=edit Opposite of FLUX/SDXL. Getting this wrong silently edits the face and preserves the teeth. Has burned us twice.
Tooth erase is mandatory Without erasing existing teeth to rgb(20,12,12), Ideogram minimally adjusts light teeth → white slab with no embrasures.
Ideogram output is always ~3:1 AR Different input AR → Ideogram pads and returns 3:1. Stretch-drawing it back costs sharpness. Keep crop near 3:1.
MediaPipe requires WebGL Won't run in headless Chromium or Node. Use harness/landmarks.py (Python mediapipe) for server-side automation.
Ideogram variance is large Never validate a generation recipe on one draw. Best-of-2 is table stakes. Test 5+ draws before shipping any pipeline change.
HIPAA: face photos are identifiers Public marketing embeds (visitor's selfie) are generally outside HIPAA scope. Chairside use IS HIPAA. Replicate/fal.ai/Resend don't sign BAAs. AWS S3 gives free BAA for true compliance path.
Instagram training data not licensed The 600 pairs from a friend's account need a written commercial license for commercial training. Dr. D's own archive is clean.
destination-in clips by alpha, not color Opaque black = alpha 255 = same as white. Blend mask canvas must default transparent or the whole crop composites.
